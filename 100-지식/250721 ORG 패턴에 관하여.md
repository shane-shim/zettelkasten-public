# 250721 ORG 패턴에 관하여

#100-지식

공유된 책임(감)은 정보의 공유, 그리고 의사결정의 투명함의 토대에서 형성되는 것 같아요. '내가 모르는 뭔가 사정이 있겠지...'라던지, '이건 왜 하는지 배경을 모르겠네' 하는 경우에는 잘 동작하지 않더라고요. 최근에 OpenAI 퇴사자의 후기가 있었는데, 거기서도 매출, 급여 등 아주 민감한 내용 이외에는 모두 다 공유된다는 얘기가 있었어요. 저에게도 당연한 것이었는데, 의외로 기본적으로 감추는, 또는 기본적으로 공유하는 습관이 안되어 있는 조직들도 많더라고요.

> 책에서는 그 보완책으로 ‘테스트 함께 보내기’라는 기법을 소개한다. 제품 백로그에 사용자 스토리뿐 아니라, 완료 여부를 판별할 수 있는 테스트 케이스를 함께 담는 방식이다.
 이건 SBE를 참고해보시면 힌트가 될 수도...

이것 관련해서는 [OrgPatterns](https://wiki.wooridle.net/OrgPatterns)도 한번 참고해보시면. Jim Coplien이 "Organization Patterns Of Agile Software Development"이라는 이름으로 낸 책도 있어요.

사실 [XP도](http://www.extremeprogramming.org/map/development.html), SCRUM도 pattern "language"인데, 그래서 각각의 practice가 연관관계를 가지고 서로 강화하는 관계이죠. 이런 system dynamics로 바라봐야 해요. Scrum의 초기 influencer 중 하나인 Mike Beedle은, 자기는 1995년 이후로는 방법론으로는 SCRUM과 OrgPatterns만을 사용해오고 있다고 [해요](https://www.scruminc.com/mike-beedle-on-early-history-of-scrum/).

아래 그림이 XP에서 말하는 feedback loop인데, 
- pair programming은 초단위로 커뮤니케이션이 일어나고,,
- Unit test는 분 단위로,,
- Acceptance test는 days 단위로 일어나야하는거죠.,
 하지만 이렇지 않은 경우를 많이 봐요. 
- unit test를 1시간에 한번씩, 하루에 한번씩, 며칠에 한번씩 몰아서 돌리는 경우도 많고. 아예 없는 경우도 있고요.,
- acceptance test도, 이게 꼭 automated test가 아니어도 되는데, 고객이, 또는 고객 관점에서 PO/PM이 직접 사용하면서 테스트해보는게, days, 그러니까 대충 2~3일에 한번씩은 일어나야 한다는거죠. 일주일 넘어가거나, 몇주에 한번씩 일어나는게 아니라. 이건 continuos integration과도 연결돼요.,
- CI를 github action 돌리는걸로 오해하는 분들이 많은데, 사실 모든 개발된 코드들은 하루마다 모두 main branch에 통합되어서 깨지지 않는 상태가 되어야 해요. 그게 daily build, continous integration이죠. 3일, 5일씩 main branch로 통합되지 않은 채 각각의 branch에서 작업하는 상태는 CI가 안일어나고 있는 상태죠. 하지만 그렇게 착각하는 경우들이 많아요. 하지만 진정한 CI는, 모든 개발자들이 개발한 코드가, 적어도 하루에 한번씩은 모두 모여서 깨지지 않는 상태가 되는 것을 말해요. 그렇게 되도록 개발의 순서와 형식을 조정해서 개발해가는거죠.

말씀주신 내용을 듣고 org 패턴을 정리해보자면 
1. 신뢰는 스크럼의 조건이 아니라 전재이다. (거의 모든 패턴의 시작점이 신뢰공통체),
-> 신뢰는 투명하게 공유하는 것에서부터 시작된다. 
1. 적은 역할 , 명확한 책임,
-> 역할이 많을 수록 책임은 희석된다. -> 중심에서 문제를 푸는 사람이 팀의 실질적 리더 
1. 작은 팀, 분산된 책임,
-> 3~7명정도의 소규모 팀은 책임을 공유하면서도 긴밀한협업 -> 스크럼의 크기는 기능이 아니라 소통 구조로 결정됨. 
1. 자기조직화팀,
-> 스스로 선택한 동료들과 일하는 팀은 높은 몰입도와 책임감 ( 프리랜서가 안되는 이유) -> 리더가 팀을 짜는 것이 아닌 미션을 기반으로 사람들을 모아야한다. 
1. 결과를 만드는 환경,
-> 외부 간섭을 차단해 팀이 집중할 수 있는 환경 -> 목적의 일치 -> 팀에 대한 자부심과 공도의 성취 
1. 항상 누군가는 진척 중이어야 한다.,
-> 일의 흐름이 멈추지 않도록 만드는 구조적 책임. -> 잔디밭을 관리하는 것처럼 매일매일.
